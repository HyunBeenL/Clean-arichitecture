# 클린 아키텍처 7장 — 우발적 중복 실험

로버트 C. 마틴 『클린 아키텍처』 **7장 「SRP: 단일 책임 원칙」** 의 `Employee` 예시를,
**테스트를 돌려서 눈으로 확인할 수 있게** 옮겨놓은 프로젝트입니다.

이 프로젝트의 목표는 하나입니다.

> **"우발적 중복(Accidental Duplication)이 대체 어떤 상황인가?"** 를 숫자로 보기

---

## 1. 7장이 말하는 SRP

흔한 오해: "클래스는 한 가지 일만 해야 한다"
→ 실제 정의: **"하나의 모듈은 하나의 액터(actor)에 대해서만 책임져야 한다"**

여기서 액터란 **그 코드의 변경을 요구하는 사람들의 집단**입니다.

책의 `Employee` 클래스는 메서드 3개가 각각 다른 액터를 섬깁니다.

| 메서드 | 요구한 부서 | 보고 대상(액터) |
|---|---|---|
| `calculatePay()` | 회계팀 | CFO |
| `reportHours()` | 인사팀 | COO |
| `save()` | DBA | CTO |

서로 다른 세 액터가 한 클래스에 묶여 있는 것 — 이게 SRP 위반입니다.

---

## 2. 무엇이 "중복"인가 (← 이 프로젝트의 핵심)

`calculatePay()` 와 `reportHours()` 는 둘 다 **"정규 근무시간"** 을 필요로 합니다.
계산식이 같아 보이니, 개발자는 당연히 중복을 제거하고 `regularHours()` 라는 함수 하나로 묶습니다.

```java
public long calculatePay() {
    long regularHours = regularHours();   // ← 공유
    ...
}

public String reportHours() {
    long regularHours = regularHours();   // ← 공유
    ...
}

private long regularHours() { ... }       // ⚠️ 문제의 함수
```

**여기서 놓친 것이 있습니다.** 두 부서가 말하는 "정규 근무시간"은 사실 같은 개념이 아닙니다.

| | 회계팀(CFO) | 인사팀(COO) |
|---|---|---|
| 정규 근무시간의 의미 | 연장수당을 지급하지 않아도 되는 시간 | 근로기준법상 연장근로가 아닌 시간 |
| 바뀌는 이유 | 급여 정책이 바뀔 때 | 노동법·근태 규정이 바뀔 때 |

지금은 두 규칙의 **계산 결과가 우연히 같을 뿐**입니다.
코드로는 한 개지만, **규칙으로는 원래 두 개**였던 겁니다.
이것이 진짜 중복이 아니라 **우발적(accidental) 중복** 이라고 불리는 이유입니다.

> **판별 기준**
> 두 코드가 지금 똑같이 생겼더라도, **서로 다른 이유로 바뀔 수 있다면** 그건 중복이 아닙니다.
> 합치는 순간 한쪽의 요구가 다른 쪽을 몰래 망가뜨리는 통로가 생깁니다.

## 3. 실험 시나리오

**근무 기록** (주 합계 32시간)

| 월 | 화 | 수 | 목 | 금 |
|---|---|---|---|---|
| 10h | 10h | 4h | 4h | 4h |

이 기록이 중요한 이유: 주 합계는 40시간을 넘지 않지만, 월·화는 하루 8시간을 넘겼습니다.
**"하루 8시간 기준"과 "주 40시간 기준"의 결과가 달라지는 지점**입니다.

**회계팀의 요청 (딱 한 건)**

> "연장수당은 주 40시간을 넘긴 시간에만 지급합니다.
>  정규 근무시간을 '하루 8시간' 기준이 아니라 '주 40시간' 기준으로 바꿔주세요."

개발자는 요청대로 `regularHours()` **한 곳만** 고칩니다.
→ [`EmployeeAfterCfoRequest`](src/main/java/com/example/srp/ch07/EmployeeAfterCfoRequest.java)
(나머지 메서드 본문은 원본과 글자 하나 다르지 않습니다. 직접 비교해 보세요.)

**결과**

| 구분 | 변경 전 | 변경 후 | 판정 |
|---|---|---|---|
| 급여 (회계팀 요청) | 680,000원 | 640,000원 | ✅ 요청한 변경 |
| 보고서 정규시간 (인사팀) | 28시간 | **32시간** | ❌ 요청한 적 없음 |
| 보고서 연장시간 (인사팀) | 4시간 | **0시간** | ❌ 요청한 적 없음 |

실제로 발생한 **4시간의 연장근로가 보고서에서 사라졌습니다.**
인사팀이 이 보고서로 연장근로 한도를 관리하고 있었다면 그대로 사고입니다.

| [`HrReportRegressionTest`](src/test/java/com/example/srp/ch07/HrReportRegressionTest.java) | 인사팀이 작성해 뒀던 테스트. **`@Disabled` 를 지우고 실행하면 빨간불** |

### ★ 꼭 해볼 것

`HrReportRegressionTest` 의 `@Disabled` 를 지우고 실행해 보세요.

```
Expecting actual:
  "[근무시간 보고서] 김개발
정규 근무시간: 32시간
연장 근무시간: 0시간"
to contain:
  "정규 근무시간: 28시간"
```

인사팀은 **아무 변경도 요청하지 않았는데** 인사팀 테스트가 깨집니다.
그리고 진짜 무서운 질문 하나 — **인사팀에 이 테스트가 없었다면?**
아무도 모르는 채로 잘못된 보고서가 몇 달간 나갔을 겁니다.
7장에서 COO가 뒤늦게 발견하고 분노하는 장면이 바로 이것입니다.

## 5. 7장의 또 다른 증상: 병합(Merge)

이 프로젝트에는 코드로 넣지 않았지만, 책은 같은 원인에서 나오는 두 번째 증상도 듭니다.

DBA가 테이블 스키마를 바꾸고(`save()` 수정), 같은 시점에 인사팀이 보고서 형식을 바꿉니다(`reportHours()` 수정).
서로 다른 팀의 개발자 둘이 **같은 파일을 체크아웃해서 머지**하게 되고,
머지는 CTO와 COO 양쪽 코드를 동시에 망가뜨릴 위험을 만듭니다.

## 6. 다음 단계

책은 이어서 해결책(`EmployeeData` + `PayCalculator`/`HourReporter`/`EmployeeSaver` 분리, 그리고 `EmployeeFacade`)을 제시합니다.
이 프로젝트에는 **아직 넣지 않았습니다.** 문제부터 확실히 체감하는 게 먼저라서요.

직접 해보고 싶다면 이 순서를 권합니다.

1. `HourReporter` 를 만들어 인사팀 규칙(하루 8시간)을 `Employee` 밖으로 꺼낸다
2. `PayCalculator` 를 만들어 회계팀 규칙(주 40시간)을 따로 둔다
3. 두 클래스가 각자의 `regularHours()` 를 갖게 한다 — **더 이상 공유하지 않는다**
4. 회계팀 규칙을 다시 한번 바꿔보고, 인사팀 테스트가 그대로 통과하는지 확인한다
